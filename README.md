# KREWLIMBER

사내 비공개 클라이밍 동호회 크루라이머의 회원 전용 사이트. 이메일·OAuth·실제 LDAP 연동 없이 `aiden.dw` 같은 사이트 자체 아이디와 비밀번호를 사용합니다.

## 기능

- 소개 페이지 없이 로그인으로 시작하는 회원 전용 베이스캠프
- 아이디·비밀번호·한글 이름·닉네임 가입과 로그인, 운영진 승인 대기
- 승인된 회원만 조회 가능한 회원 목록, 닉네임·한글 이름 검색·난이도 필터
- 내 프로필·가입 상태·비밀번호 관리
- 분기별 참여·번개 개최·색상별 완등 1위 타이틀, 공동 순위와 과거 분기 조회
- 누적 기록 기반 업적 목록과 대표 업적 선택, 멤버 이름 옆 타이틀과 이름 아래 대표 업적
- 운영진의 분기 기록 입력과 업적 정의 추가·삭제
- 공지사항 목록·상세·검색·고정 및 운영진 작성·수정·삭제
- 상품 카드·상세·포인트 교환 신청과 내 잔액·포인트·교환 내역
- 운영진의 상품·재고·판매 상태, 포인트 지급·정정과 교환 완료·취소 관리
- 운영진의 회원 승인·반려·정지·권한 변경과 변경 이력
- 운영진 신원 확인 후 일회용 복구 코드로 비밀번호 재설정

## 로컬 실행

Node 24와 pnpm 10을 사용합니다.

```sh
pnpm install
cp deploy/.env.local.sample deploy/.env.local
pnpm dev
```

주소: http://localhost:4173. `HOST=127.0.0.1`, `APP_ORIGIN=http://localhost:4173`가 기본입니다. 접속 주소와 APP_ORIGIN이 정확히 일치해야 변경 요청을 허용합니다. 앱의 회원 데이터는 Supabase PostgreSQL에 저장하고 상품 이미지는 비공개 Storage 버킷에 저장합니다. `deploy/.env.local`에 PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY를 설정해야 합니다. 키는 브라우저에 전달하지 않습니다. 기존 SQLite는 이전 원본·테스트 용도로 보존합니다.

`PHASE`로 `deploy/.env.local`, `deploy/.env.production` 등 환경 파일을 선택합니다. 서버와 관리자 생성 명령은 같은 선택 규칙을 사용하며, NODE_ENV=production이면 기본으로 deploy/.env.production을 읽습니다. 외부에서 지정한 환경변수가 파일 값보다 우선합니다.

## 첫 관리자

기본 계정이나 기본 비밀번호는 없습니다. 터미널에서 다음 명령을 실행하고 아이디·닉네임·비밀번호를 입력하세요. 비밀번호는 화면과 명령 인자에 노출되지 않습니다. 일반 가입은 항상 회원·승인 대기로 생성됩니다.

```sh
pnpm admin:create
```

운영 환경 파일을 사용하는 직접 실행에서는 `NODE_ENV=production pnpm admin:create`로 실행합니다. 기존 회원과 다른 미사용 아이디로 생성합니다. 첫 관리자로 로그인한 후 일반 계정을 승인하거나 관리자로 변경할 수 있습니다. 마지막 관리자의 강등·정지는 거부됩니다.

비밀번호 분실 회원은 운영진에게 별도로 연락합니다. 운영진이 본인을 확인한 뒤 회원 관리의 열쇠 버튼으로 복구 코드를 발급해 본인에게 전달합니다. 회원은 로그인 화면의 `비밀번호를 잊으셨나요?`에서 아이디, 코드, 새 비밀번호를 입력합니다. 코드는 30분 내 한 번만 사용 가능하며 재발급 시 이전 코드는 무효화됩니다.

## 운영 배포

지속적으로 켜져 있는 Node 서버와 영구 디스크가 필요합니다. 정적 GitHub Pages나 임시 파일시스템 서버리스 호스팅에는 사용할 수 없습니다. Vercel Hobby + Supabase Free 배포 구성을 포함합니다. 자세한 전환 절차는 아래를 참고하세요.

1. 도메인의 HTTPS를 처리하는 리버스 프록시와 영구 디스크가 있는 서버를 준비합니다.
2. 운영 환경에 APP_ORIGIN(실제 HTTPS 출처)과 TRUST_PROXY(백엔드가 관측하는 실제 프록시 IP 또는 CIDR)를 설정한 뒤 `docker compose up --build -d`로 실행합니다. 운영 서버는 TRUST_PROXY 누락 시 시작하지 않습니다. 전체 주소를 신뢰하도록 설정하지 말고, 프록시가 외부의 X-Forwarded-For 값을 덮어쓰거나 올바르게 추가하도록 구성합니다.
3. 프록시의 목적지를 `127.0.0.1:4173`으로 지정합니다. 해당 포트는 인터넷에 직접 노출하지 않습니다.
4. `docker compose exec web node --import tsx scripts/create-admin.ts`로 첫 관리자를 생성합니다.
5. 가입·승인·회원 목록 조회·로그아웃을 실제 HTTPS 주소에서 확인합니다.

운영 모드는 HTTPS APP_ORIGIN을 필수로 하며 Secure/HttpOnly/SameSite 세션 쿠키를 사용합니다. 인증·권한 검증은 서버에서 수행하고 비밀번호는 개별 salt와 scrypt(N=32768,r=8,p=3)로 해시합니다. 세션·복구 코드는 해시만 DB에 저장합니다. 비밀번호 변경·복구 시 모든 세션을 삭제하며, 정지나 권한 변경 시 기존 세션도 폐기합니다. 변경 요청은 APP_ORIGIN과 Origin 헤더를 대조합니다.

단일 서버·단일 프로세스 운영을 전제로 합니다. 지정한 프록시만 신뢰해 원본 클라이언트 IP로 로그인·가입 제한을 분리합니다. 비밀번호 변경 시도는 로그인한 계정별로 제한합니다. 회사 NAT처럼 원본 공인 IP 자체가 같은 사용자는 IP 제한을 공유하므로 운영 정책에 맞춰 가입 제한(기본 IP당 시간당 5회)과 로그인 실패 제한(IP당 15분에 15회)을 조정할 수 있습니다. 여러 인스턴스로 확장할 때는 공유 DB와 공유 제한 저장소가 필요합니다.

## 백업

SQLite DB와 WAL 파일은 함께 일관성을 보장해야 합니다. 실행 중 DB 파일만 복사하지 말고 SQLite의 `.backup` 기능이나 서버를 중지한 상태의 볼륨 스냅샷을 사용합니다. 복구 후 로그인 세션·복구 코드를 폐기하고, 별도 환경에서 복원과 회원 조회를 검증하세요. DB에는 개인정보와 비밀번호 해시가 있으므로 백업도 접근을 제한합니다.

## 구조

`src/pages` 화면, `src/components` 공통 UI, `src/hooks` 로그인·조회 상태, `src/apis` API 클라이언트, `src/types` 공유 타입, `src/consts` 표시 상수, `server` 인증·권한·DB, `scripts` 관리자 생성, `tests` API 통합 테스트.

로고와 춘식이 이미지는 제공받은 원본을 수정하지 않고 사용합니다. 파비콘에는 이미지 1을, 가입·로그인·베이스캠프 화면과 OG 및 소셜 공유 메타 태그에는 이미지 2를 사용합니다. 공유 이미지의 절대 주소는 서버 시작 시 APP_ORIGIN을 기준으로 설정됩니다. 글꼴은 Google Fonts를 사용하며 네트워크에 접근할 수 없으면 시스템 글꼴로 표시합니다.

## 타이틀과 업적

명예의 전당은 분기별 클라이밍 참여·번개 개최·더클라임 빨강/핑크/보라 완등 1위를 계산합니다. 동률은 공동 보유자로 표시하며 0건과 비활성 회원은 제외합니다. 멤버 카드에는 한국 시간 기준 현재 분기 타이틀을 표시하고 과거 분기는 명예의 전당에서 조회합니다.

내 정보의 업적은 전체 분기 기록을 누적해 달성을 계산합니다. 달성한 업적 하나를 대표로 고르거나 해제할 수 있습니다. 기록 정정으로 조건을 잃거나 정의가 삭제되면 대표 선택도 해제됩니다. 운영진은 크루 관리의 분기 기록과 업적 관리에서 수치·조건을 관리합니다. 활동 이벤트를 자동 수집하는 기능은 아직 연결하지 않았습니다. 기존 자유 형식 성과 데이터와 API는 보존하며 새 화면은 분기 타이틀을 사용합니다.

## 테스트 유저

`server/demo-fixtures.ts`에 관리자·복수 타이틀·공동 1위·대표 업적만 보유·대표 미선택·미획득·승인 대기·정지 등 10개 예시 계정이 정의되어 있습니다. 기본 비밀번호는 테스트 전용 `Krew-Test-2026!`이며 기존 계정의 비밀번호·역할·가입 상태·세션은 덮어쓰지 않습니다.

`DEMO_DATABASE_PATH`를 명시하고 `pnpm demo:seed`를 실행합니다. 대상은 운영 모드가 아닌 OS 임시 디렉터리의 `krewlimber-preview.<문자열>/test.sqlite` 또는 `demo.sqlite`로 제한합니다. 일반 회원 DB와 운영 모드에서는 실행을 거부하며 서버 시작 시 자동 실행하지 않습니다. 반복 실행하면 데모 프로필·분기 기록·대표 선택을 예시 값으로 갱신합니다.

- `test.admin`: 관리자와 업적 선택
- `test.aiden`: 복수 타이틀과 모든 기본 업적 달성
- `test.red`, `test.host`, `test.twin`: 색상·번개 타이틀과 공동 1위
- `test.badge`, `test.unset`, `test.rookie`: 대표 업적만 보유·대표 미선택·미획득
- `test.pending`, `test.rest`: 승인 대기·정지

## 공지사항과 포인트 마켓

공지사항은 승인 회원만 읽고 운영진이 관리합니다. 일반 텍스트 본문, 상단 고정, 제목·내용 검색과 페이지 이동을 지원합니다. 작성·수정·삭제는 감사 기록에 남습니다.

포인트는 운영진이 사유와 함께 지급하거나 정정합니다. 가입 시 기본 포인트나 자동 활동 적립은 없습니다. 회원이 교환을 신청하면 포인트와 재고가 즉시 차감됩니다. 처리 대기 중에는 본인 또는 운영진이 취소할 수 있으며 포인트·재고를 한 번만 반환합니다. 완료 후 취소는 거부됩니다. 기존 교환 내역에는 신청 당시 상품 이름·가격·이미지가 보존됩니다.

동일한 신청 ID의 재전송은 원래 결과를 반환합니다. 포인트 지급·정정도 같은 작업 ID의 재시도는 한 번만 반영합니다. 회원이 확인한 상품 버전과 현재 값이 다르면 차감 없이 다시 확인하도록 안내합니다. 포인트 원장·재고·신청·감사 기록은 하나의 SQLite 트랜잭션으로 처리합니다. 운영진이 재고를 정정할 때도 대기 신청의 예약 수량을 포함해 최대 1,000,000개를 넘지 않도록 해 취소 시 반환을 보장합니다. 상품 변경과 교환·취소는 상품 버전을 갱신합니다. 오래된 관리자 편집은 저장을 거부해 동시 교환으로 바뀐 재고가 덮어써지지 않도록 합니다. 상품 이미지는 HTTPS 또는 사이트 내부 경로를 쓰며, 없으면 분류별 대체 그림을 표시합니다.

테스트 상품·공지·포인트·신청 예시는 기존 임시 테스트 계정을 만든 뒤 `DEMO_DATABASE_PATH`를 지정하고 `pnpm demo:boards`로 추가합니다. `demo:seed`와 같은 임시 DB 경로 제한을 적용하며 운영 모드는 거부합니다. 반복 실행해도 이미 변경한 상품·포인트 잔액·교환 내역을 초기화하지 않습니다.

운영진은 마켓 상단의 상품 등록과 상품 상세의 상품 수정에서 이미지 파일과 판매 상태를 관리할 수 있습니다. 판매 중지 상품은 회원 목록에서 숨겨지며 크루 관리의 마켓 관리에서 다시 판매할 수 있습니다. JPG·PNG·WebP(최대 4MB, 2,500만 화소)를 선택하면 미리보기를 표시하고 저장 시 서버에 업로드합니다. 서버는 긴 변 최대 1800px WebP로 다시 저장하며, 이미지 조회에도 승인 회원 권한을 검사합니다.

업로드 파일 저장 위치는 `UPLOADS_DIR`로 지정합니다. 기본값은 `DATABASE_PATH` 파일과 같은 디렉터리의 `uploads`이며, 기존 Docker 영구 볼륨 `/app/data`에 함께 저장됩니다. 운영 서버에 옮길 때 SQLite DB와 uploads 디렉터리를 함께 이전·백업해야 합니다. DB만 복구하면 상품 이미지는 복구되지 않습니다. 기존 교환 내역의 이미지 보존을 위해 업로드 파일은 자동 삭제하지 않습니다.

## Vercel + Supabase

실서비스 서버는 PostgreSQL을 사용합니다. SQLite는 기존 데이터 이전과 독립된 테스트/데모 fixture에만 사용합니다. Supabase Auth 대신 기존 아이디·비밀번호·승인·세션을 유지합니다.

1. Node 24에서 `pnpm install --frozen-lockfile`을 실행합니다.
2. `deploy/.env.production.sample`을 참고하여 Git에서 제외되는 `deploy/.env.production`에 PG 연결 값과 Storage 서버 키를 입력합니다. Transaction pooler(6543)를 사용하며 공식 Supabase CA 인증서 검증을 유지합니다.
3. `pnpm supabase:check`로 접속을 확인하고 `pnpm supabase:migrate`로 마이그레이션을 적용합니다. 마이그레이션은 명시적으로 실행하며 앱 시작 때 실행하지 않습니다.
4. 기존 SQLite가 있을 때만 `pnpm supabase:import`를 한 번 실행합니다. 원본 백업을 만든 뒤 비어 있는 대상에 회원·기록·이미지를 이전하며 세션·복구 코드는 이전하지 않습니다. 기존 사용자가 있는 대상에는 덮어쓰기를 거부합니다.
5. private `market-images` 버킷을 만들고 `SUPABASE_SERVICE_ROLE_KEY`에 서버 전용 secret key를 설정합니다. 신규 `sb_secret_` 키와 기존 service-role JWT를 지원합니다. 브라우저 공개 키로 대체하지 않습니다.
6. Vercel 프로젝트에 PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD, SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY 및 정확한 HTTPS APP_ORIGIN을 Production 환경변수로 등록합니다. 비밀은 sensitive로 저장합니다. VITE_ 접두사를 사용하지 않습니다.
7. `vercel --prod`로 배포합니다. 처음에는 vercel.app 도메인을 사용하며, 도메인을 변경하면 APP_ORIGIN도 바꾸고 재배포합니다. 임의 Preview 도메인은 변경 요청 출처로 허용하지 않습니다. 운영 DB를 Preview 기능 테스트에 공유하지 마세요.

로컬 개발도 `deploy/.env.local`의 PostgreSQL/Storage 설정을 사용합니다. 두 환경 파일에 동일한 DB를 지정하면 실제 데이터를 함께 변경하므로 개발·운영 DB 분리를 권장합니다. SQLite 원본의 세션은 이전하지 않으므로 기존 회원은 이전한 비밀번호로 다시 로그인합니다. `SMOKE_USERNAME=<승인 회원 아이디> pnpm supabase:smoke`는 실제 DB의 회원 읽기 API를 확인하고 테스트 세션을 즉시 폐기합니다.

Vercel API 진입점은 플랫폼이 덮어쓰는 X-Forwarded-For 한 홉을 신뢰합니다. 일반 Node 서버에서는 TRUST_PROXY에 실제 리버스 프록시 IP/CIDR을 지정합니다. 로그인 제한은 PostgreSQL에서 공유하며 주문·포인트·취소는 같은 연결의 트랜잭션과 DB advisory lock으로 직렬화합니다. 이미지 입력 한도는 Vercel 요청 크기를 고려해 4MB입니다. 포인트·회원·공지 기능은 기존 경로를 유지합니다.

Supabase Free는 비활성 시 중지될 수 있고 자동 백업을 제공하지 않으므로, PostgreSQL과 private Storage 이미지를 별도로 백업해야 합니다. 유료 플랜 자동 전환이나 결제 수단 등록은 이 구성에 포함하지 않습니다.

## 회원 권한

회원은 승인 후 회원 공간을 이용합니다. `staff`는 운영진, `admin`은 관리자이며 현재 두 역할 모두 회원 승인·권한 변경·비밀번호 복구·공지·기록·업적·마켓 관리 기능을 동일하게 사용할 수 있습니다. 마지막 활성 관리자는 강등·정지할 수 없습니다. 추후 권한 분리는 공통 `hasManagementAccess` 정책과 서버 검증을 함께 조정합니다.

승인 회원이 로그인하면 베이스캠프(`/`)로 이동합니다. 승인 대기 회원은 내 가입 상태(`/me`)를 확인합니다.

## 한글 이름

회원가입 시 한글 이름을 2~30자로 필수 입력합니다. 아이디·닉네임과 별도인 `fullName`으로 저장하며 내 프로필에서 수정할 수 있습니다. 멤버 목록과 회원 관리에 표시하고, 멤버 목록에서는 닉네임 또는 한글 이름으로 검색합니다. 이전 클라이언트의 프로필 저장 요청에 이름 항목이 없어도 기존 이름을 유지합니다.

### 암장지도와 등반 기록

`LOCAL_PREVIEW=1 pnpm dev`는 운영 PostgreSQL과 분리된 `data/local-preview.sqlite`를 사용합니다. 운영 모드에서는 사용할 수 없습니다. 테스트 계정 `test.admin` / `Krew-Test-2026!`으로 로그인합니다. 기존 운영 계정·비밀번호·회원 데이터는 복사하지 않습니다.

암장지도는 `deploy/.env.local`의 `VITE_KAKAO_MAP_KEY`(JavaScript 키)와 Kakao Developers에 등록한 JavaScript SDK 도메인 `http://localhost:4173`이 필요합니다. 키가 없거나 SDK 로딩이 실패해도 암장 목록과 개인 기록 기능을 사용할 수 있습니다. 카카오 장소 검색으로 추가한 암장은 좌표가 함께 저장됩니다. 등록된 암장은 모든 승인 회원이 공유하며, 암장명과 선택 지점명을 별도 저장합니다. 상단 암장 필터는 등록 데이터에서 자동 생성합니다.

DB 변경은 `pnpm supabase:migrate`로 명시적으로 적용합니다. 로컬과 운영이 같은 DB를 사용하면 데이터도 공유됩니다. 기록은 본인만 조회/수정/삭제 가능하고 회원 누구나 공용 암장과 난이도를 추가할 수 있습니다. 레벨 집계 API `/api/me/level`은 저장된 회원 레벨과 방문·완등·기존 획득 업적 집계를 반환합니다. 기존 수동 활동·업적·포인트를 덮어쓰지 않습니다. 자동 승급 기준은 추후 추가합니다.

공용 암장 등록은 카카오 장소 ID로 중복을 막으며 난이도 목록도 한 트랜잭션에 저장합니다. `202611060006_gym_community.sql`에 장소 ID와 난이도 순서, 회원 댓글 스키마가 있습니다. 댓글은 승인 회원이 읽고 작성하며 본인 수정·삭제와 운영진·관리자 삭제를 지원합니다. 최신 100개를 표시합니다. 지도/검색 SDK 오류·타일 로딩 실패는 이용 한도 또는 연결 오류로 안내하고 기록 기능을 유지합니다. SDK가 HTTP 상태를 제공하지 않으면 쿼터 소진이라고 단정하지 않습니다. 무료 한도: 지도 Web SDK 일 300,000건, 키워드 검색 일 100,000건(공식 문서 2026-11-06 확인; 첫 활성화 앱 조건은 Kakao Developers 쿼터 참고). 유료 API 설정은 변경하지 않습니다.

### 회원 레벨제

레이팅 점수 대신 `src/consts/levels.ts`의 Lv.0~Lv.11 체계를 사용합니다. 신규·기존 회원 기본값은 Lv.0이며, 자동 승급 조건이 없으므로 운영진·관리자가 관리 화면에서 지정합니다. 내 정보의 `/api/me/level` 집계와 멤버 목록 모두 같은 저장 레벨을 표시합니다. 회원 본인은 프로필 수정으로 레벨을 변경할 수 없습니다. `202611060007_member_levels.sql`은 0~11 정수 제약을 추가합니다.

### 운영 지도 설정과 업적

운영 빌드에는 `VITE_KAKAO_MAP_KEY` JavaScript 키가 필요합니다. Kakao Developers의 JavaScript SDK 도메인에 `https://krewlimber.vercel.app`을 추가하고 로컬 도메인은 유지합니다. 구매 도메인을 연결하면 해당 HTTPS 도메인도 추가합니다.

난이도는 지점마다 낮은 난이도가 1이고 숫자가 커질수록 높습니다. 업적 추가 UI와 생성 API는 제공하지 않습니다. 기존 업적 조회·대표 선택은 유지하며, 향후 별도 배치 집계 방식으로 확장할 예정입니다.

### 복원된 프로필·타이틀·업적

인스타그램 계정은 내 정보에서 선택적으로 입력하고 승인 회원 목록에 링크로 표시합니다. 계정명, @계정명, Instagram HTTPS 프로필 주소를 입력할 수 있으며 비우면 삭제됩니다. 기존 클라이언트가 필드를 생략하면 저장된 값을 유지합니다.

보라 칭호는 `보라 클래스`입니다. 추가 분기 타이틀은 `세계관 최강자`(더클라임 회색 완등), `번개 붙박이`(번개 참여), `포인트 채굴왕`(포인트 순획득), `마켓 큰손`(포인트 실사용)입니다. 회색은 공용 암장·방문·난이도 기록에서 계산하고, 번개 참여와 기존 여섯 활동 지표는 기존 운영진 입력 방식을 유지합니다. 포인트 획득은 지급액과 차감 정정의 합계(최소 0), 사용은 취소되지 않은 교환 신청·완료 금액입니다. 취소하면 원래 신청한 분기의 실적에서 제외합니다. 분기는 한국 시간 기준입니다.

번개 참여 100회, 포인트 획득·사용 각각 1,000·5,000·10,000P 업적을 추가합니다. 대표 선택과 회원 목록도 같은 기록을 사용합니다. 정정·취소로 조건을 잃으면 해당 대표 선택을 해제합니다. 새 PostgreSQL 마이그레이션을 적용한 뒤 새 서버 버전을 배포해야 하며, 서버 시작 시 업적을 재생성하지 않습니다. 운영 DB 적용은 기존 `pnpm supabase:migrate` 절차로 별도로 진행합니다.

## 이벤트 빙고

참가 경로는 `/event/bingo`, 운영진 경로는 `/event/bingo/admin`입니다. 회원·비회원 모두 운영진이 발급한 8자리 조 코드로 입장하고 같은 조의 숫자·5×5 판·체크 상태를 공유합니다. 준비 단계에서는 코드로 입장한 누구나 획득 숫자를 추가하거나 판을 배치할 수 있고, 진행 중 체크·해제는 기존 로그인을 마친 승인 회원만 가능합니다. 비회원과 미승인 회원은 관람할 수 있습니다.

운영진은 최대 번호 n(25~1000)을 정해 이벤트를 만들고 조 이름을 등록합니다. 기본 입력값은 75입니다. 준비 현황을 확인하고 빙고를 시작하면 숫자 수집·번호 범위·판 배치를 잠급니다. 완성 판이 한 조 이상 있어야 시작할 수 있으며 미완성 조는 순위에서 제외합니다. 종료하면 체크도 잠기고 가로·세로·대각선 최대 12줄을 기준으로 최종 순위를 표시합니다. 동점은 공동 순위(1,1,3)이며 중앙 FREE 칸은 없습니다. 번호는 오프라인에서 호명합니다.

숫자는 획득한 것 중 서로 다른 25개를 선택합니다. 상단 가로 목록의 전체 보기에서 미획득 번호는 회색 비활성화되고, 선택 번호를 빈칸에 누르면 배치됩니다. 채운 칸을 누르면 비울 수 있으며 판에서 뺀 숫자만 획득 목록에서 삭제할 수 있습니다. 정정 중 획득 숫자가 25개 아래로 줄어도 기존 칸을 비울 수 있으며, 새 배치는 다시 25개를 모은 뒤 가능합니다. 최대 번호를 줄일 때 기존 획득 숫자가 범위를 벗어나면 저장을 거부합니다.

진행 중에는 같은 조회 결과에서 계산한 줄 수와 현재 순위를 나란히 표시하고, 동점은 `공동 N위`로 표시합니다. 1·2·3위는 금·은·동색으로 강조하며 미완성 조는 순위가 없습니다. 체크 저장 중에는 누른 칸만 피드백을 표시하고 다른 칸의 색상·투명도를 유지합니다.

상태는 3초마다 동기화하고 새로고침해도 보존합니다. 저장 요청의 이벤트·조 ID와 revision을 함께 검증해, 다른 탭에서 조를 바꾼 경우와 오래된 저장 요청을 거부하고 최신 상태를 다시 표시합니다. 조 세션은 24시간 유효한 HttpOnly 쿠키이고 운영 HTTPS에서는 Secure로 발급합니다. 조 코드는 관리자만 다시 조회할 수 있으며, 진행 중·최종 순위도 조 입장 이후에만 노출합니다. 시작·종료·판 저장은 같은 DB 트랜잭션에서 검증하고, 회원 권한은 체크 시마다 다시 확인합니다. 종료 후 새 이벤트를 만들면 이전 기록을 보존하며 새 조 코드가 필요합니다.

신규 PostgreSQL 마이그레이션 `20261110052911_event_bingo.sql`을 먼저 적용한 뒤 새 서버를 배포해야 합니다. 기존 회원 데이터와 인증은 변경하지 않으며 이 작업 자체가 운영 마이그레이션이나 배포를 실행하지는 않습니다.
